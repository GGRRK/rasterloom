# Releasing Rasterloom

Development happens in the **private** repository `GGRRK/rasterloom` (full history, lane
branches, milestone pushes). Every public release is published to a **separate public
repository** as one clean snapshot commit. Nothing from the private history, and nothing that
identifies the developer's machine, reaches the public repository.

This document is the procedure. Each step names the command and the evidence it must produce;
a step without its evidence has not happened. No step is ever run by an agent without the
maintainer's explicit go-ahead for that release.

## 0. Preconditions (private repo)

1. The release branch is green in CI on the exact commit being released:
   `build-test` passed, including `goldens`, `goldens_determinism` and the `mutation_gate`
   (no `RL_MUTATION_ALLOW_PENDING`), and the `package` job produced
   `Rasterloom-x86_64.AppImage` plus `Rasterloom-x86_64.AppImage.sha256`.
2. The CI run's `visual-artifacts` were downloaded and the contact sheets were looked at
   (`blend_modes.png`, one sheet per golden domain, and `gui-contact-sheet.png` once the GUI lane
   provides it).
3. `docs/PARITY.md` and the README headline were regenerated by that run
   (`tools/gen_parity.py ... --readme README.md`) and committed; the numbers in any release note
   are copied from that file, never typed.
4. `THIRD-PARTY-NOTICES.md` from the same run lists every bundled component with a resolved
   version and license text (the generator exits non-zero otherwise).
5. The version is bumped everywhere it lives (`project(... VERSION x.y.z)` in `CMakeLists.txt`;
   `rasterloom --version` and `rasterloom-cli --version` print it), and the private repo is
   tagged `vX.Y.Z-private` for traceability.

## 1. Build the public tree (a scratch directory, never the dev clone)

```sh
git -C <dev-clone> archive --format=tar vX.Y.Z-private | tar -x -C /tmp/rl-public
```

`git archive` exports tracked files only: no `.git`, no `.worktrees/`, no build directories,
no `.venv/`, no `tests/output/`. Then remove what is private by nature:

- internal agent/briefing material if any exists at release time (for example session notes or
  lane briefs) - the build spec, math docs and research notes stay, they are the design record;
- any file under `data/` or `docs/` that the privacy scrub below flags and that cannot be fixed.

## 2. Privacy scrub (every item must be checked, with the command output kept)

Run from the public tree root. Every command must print nothing (or only lines you have
explicitly reviewed and accepted). This file defines the patterns, so it is excluded
(`X=--exclude=RELEASE.md`):

```sh
# personal e-mail addresses (the GitHub noreply form is the only allowed address)
grep -rInE $X '[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}' . | grep -v 'users.noreply.github.com' \
  | grep -vE 'noreply@anthropic\.com|@example\.(com|org)'
# absolute home paths and user names
grep -rInE $X '/home/[A-Za-z0-9_-]+|C:\\Users\\|/Users/[A-Za-z]' .
# machine specifics: host names, hardware, local tool paths, personal locations
grep -rInEi $X 'scar ?18|rtx ?5090|hyprland|arch linux|\.worktrees|scratchpad|claude-session' .
# secrets and tokens
grep -rInE $X '(ghp_|gho_|github_pat_|xox[bp]-|AKIA)[A-Za-z0-9_]{10,}|BEGIN [A-Z ]*PRIVATE KEY' .
```

Checklist (tick each in the release issue):

- [ ] No personal e-mail address anywhere (source, docs, `AUTHORS`, commit metadata).
- [ ] No absolute `/home/...` (or Windows `C:\Users\...`) path in any file, generated report or
      notice file. `THIRD-PARTY-NOTICES.md` may name `/usr/share/...` system paths only.
- [ ] No machine details: host name, laptop model, GPU, desktop environment, local directory
      layout, scratch or worktree paths. (The BUILD-SPEC addendum describes the commissioner's
      machine: reword that paragraph to "the Linux development machine" in the public tree.)
- [ ] No session links, agent transcripts or `Claude-Session:` trailers.
- [ ] No tokens, keys, `.env` files or credential helpers.
- [ ] Images and PNG goldens carry no metadata chunks with personal data (our PNG writer emits
      none; check any hand-added asset with `python3 -c "from PIL import Image; print(Image.open(F).info)"`).

## 3. One snapshot commit under the GitHub noreply identity

**Public repository name (first release only).** Before the public repository exists, propose a
name (for example `GGRRK/rasterloom`, or `GGRRK/rasterloom-public` while the private repository
holds the plain name) and **ask the commissioner to confirm it**. Do not create the repository, and
do not write its name into release notes, the README or packaging metadata, until they have
answered. A public repository name is hard to take back (links, stars, forks and package indexes
keep the old one), so it is never chosen by default. Record the confirmed name here, then the
maintainer creates the repository.

The public repository receives exactly one commit per release on `main`, authored and committed by
the noreply identity:

```sh
cd /tmp/rl-public
git init -b main && git remote add origin git@github.com:GGRRK/<public-repo>.git
git fetch origin main && git reset --soft origin/main     # skip for the very first release
git add -A
GIT_AUTHOR_NAME=GGRRK GIT_AUTHOR_EMAIL=<id>+GGRRK@users.noreply.github.com \
GIT_COMMITTER_NAME=GGRRK GIT_COMMITTER_EMAIL=<id>+GGRRK@users.noreply.github.com \
  git commit -m "Rasterloom vX.Y.Z"
git log -1 --format='%an <%ae> / %cn <%ce>'               # must show the noreply address twice
git tag -a vX.Y.Z -m "Rasterloom vX.Y.Z"
git push origin main vX.Y.Z                                # maintainer's explicit go only
```

`<id>` is the numeric GitHub user id (`gh api user --jq .id`). Never push the private history,
never `git push --mirror`, never add the private repo as a remote of the public tree.

## 4. GitHub Release

The distributable AppImage comes only from the CI packaging job (ubuntu:22.04 container,
Qt 6.9.3), never from a local Arch build:

```sh
sha256sum -c Rasterloom-x86_64.AppImage.sha256            # must print OK
gh release create vX.Y.Z -R GGRRK/<public-repo> \
  --title "Rasterloom vX.Y.Z" --notes-file RELEASE-NOTES.md \
  Rasterloom-x86_64.AppImage Rasterloom-x86_64.AppImage.sha256
```

Release notes contain: the parity headline copied from `docs/PARITY.md`, what changed, the
tester handoff block from BUILD-SPEC (`chmod +x`, glibc >= 2.35 requirement), known limitations
("what cannot be verified" from BUILD-SPEC), and a link to `THIRD-PARTY-NOTICES.md`. A release
always gets a new version; assets of an existing release are never overwritten.

## 5. After publishing

- Download the release assets from the public page and verify the checksum again.
- Run the downloaded AppImage's self-test once (`APPIMAGE_EXTRACT_AND_RUN=1 ./Rasterloom-x86_64.AppImage --selftest`).
- Record the public commit hash and tag next to the private `vX.Y.Z-private` tag.

## 6. Running the AppImage many times (uruntime extract-and-run)

The AppImage runtime is uruntime built with `URUNTIME_EXTRACT=2`: when FUSE is missing (containers,
CI, some minimal distros), or when `APPIMAGE_EXTRACT_AND_RUN=1` is set, it extracts the bundle to a
temporary directory and runs it from there. **Parallel launches of one AppImage in that mode race on
the extraction**: one launch can be writing a binary while another tries to execute it, and fails with
`Text file busy` (`ETXTBSY`). A single interactive launch is unaffected.

For any batch run (every golden through the shipped bundle, a test matrix, a benchmark loop,
`xargs -P`), extract once and run the extracted tree, as the CI `package` job does:

```sh
mkdir -p extracted && cd extracted && ../Rasterloom-x86_64.AppImage --appimage-extract >/dev/null
./squashfs-root/AppRun --selftest            # the CLI: ./squashfs-root/AppRun --cli --render-script ...
```

Launches of the extracted tree may run in parallel. Delete `extracted/` afterwards.
