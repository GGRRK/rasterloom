# Rasterloom normative math — 50: resolutions

Status: **normative**. Where docs 00–40 are silent or ambiguous, the readings below are binding. They
were taken while writing the NumPy reference, the golden corpus and the compositing core on
2026-09-26, and the reference and goldens already implement them, so any new implementation must
match them. A reading listed here that contradicts docs 00–40 loses to the doc, unless the lead's
rulings in section 0 say otherwise.

## 0. Lead rulings (2026-09-26)

1. **Filters and the selection:** a filter uses the selection only when the op says
   `"coverage": {"src": "selection"}` (doc 20 §B0.2 wins over the general sentence in doc 30 §9). The
   GUI passes that coverage automatically when a selection is active.
2. **Lock transparency** applies to painting ops (brush, clone, eraser, gradient tool, bucket) and to
   filters (doc 20 §B0) only. `transform`, `flip` with a layer, the canvas-geometry ops, merges and
   Apply Mask ignore it.
3. **Doc 40 parity note 10** ("recolours with the unlocked source-over colour") is superseded by doc
   40 §3.8 / C8a: source-atop, alpha byte kept.
4. **History:** every op except `undo` pushes exactly one record, including ops that end up
   changing nothing. `undo` pushes no record; there is no redo in scripts. `steps` range `[1, 1000]`.
5. **Script shape:** `canvas`, `ops` and `out` are required; `out` must be `"png8"`; unknown top-level,
   canvas or op keys, duplicate keys and NaN/Infinity literals are script errors. `int` fields accept
   only JSON integer tokens (`2.0` is an error). The harness strips its own top-level keys (`expect`,
   `equal_to`) before either renderer sees a script.
6. **Rect components** with magnitude above 2^53 are script errors (both sides must reject, never
   crash).
7. **Doc 60 exists (2026-09-26):** `docs/math/60-editing-ops.md` defines `delete_layer`, `set_name`,
   `duplicate_layer`, `set_adjustment`, `set_group_mode` and `select_alpha`, the node `name`
   property (display label only; ids are immutable, so the GUI-local `rename_layer` is retired), and
   mutation hooks 40 and 41. It supersedes doc 20 A9's "params are fixed at creation". Its goldens are
   generated by `tests/scripts/gen/gen_editing.py` into `tests/scripts/.pending-editing/` (skipped by
   the harness) until both implementations land; `gen_editing.py --activate` moves them to
   `tests/scripts/editing/`.

## 1. C++ core (compositing, script engine)

- 00-conventions C8a / task brief vs doc 30 §2: the brief asks for a selection 'active flag', but doc 30 §2 says there is no separate stored flag and an empty selection means no selection. I followed doc 30: Selection::active() is derived (true iff any mask byte is non-zero), so it can never disagree with the mask.
- C10 'every document-changing op pushes exactly one record': it is unclear whether an op that ends up changing nothing (e.g. merge_visible with no visible node, set_opacity to the current value) counts. I push one record for EVERY op except `undo`, including no-ops, which matches doc 40 §6 (a stroke that changes no pixel still commits a record). The reference must do the same, or `undo` after a no-op will diverge.
- Doc 40 §2.5 vs C10: C10 says steps is 'int >= 1'; doc 40 adds 'range [1, 1000]'. I used [1, 1000] and made 'more steps than records' a script error.
- Doc 10 §11 'Script shape (fixed)': it does not say whether `out` may be omitted. I made `out` required and allowed only "png8". `canvas.bg` defaults to "#00000000" as the doc states. Unknown top-level and canvas keys are errors.
- C9 'Integers must be integral JSON numbers' vs doc 20 'must be JSON integers': I took the stricter literal reading. Only integer tokens are accepted for int fields, so 8.0 and 1e2 are rejected as not a JSON integer.
- Doc 10 §11 rects: no bound is stated for x, y, w, h. To avoid int64 overflow in x+w I reject components outside ±(INT64_MAX/4), as a script error, never a clamp. Separately, the gradient parameter t = (x - rx)/(rw - 1) is computed as double(int64)/double(int64); this matches Python only while the operands are below 2^53 (Python int/int division is correctly rounded on the exact integers).
- Doc 20 A9 'placement fields = add_layer's': I took these to be only `id` and `parent` (top insertion). add_layer's content-fill fields (fill, rect, color, ...) are rejected on add_adjustment as unknown fields.
- Doc 10 §11 ids: 'root' is reserved and names the root container. I treat `root` as a script error in every field that expects a layer (set_*, masks, move_layer id, merge_down), because the root is not a node with properties.
- Doc 10 §9.1: the precondition 'the node directly above U does not have clip = true' is applied literally to the flag, even when that node is hidden.
- Mutation 2 (doc 10 §13) says to evaluate B on premultiplied operands, but the integer modes (hMix, dkCl, lgCl) take bytes. In the mutated path only, I re-quantise the premultiplied operands with q() to feed those modes. Mutation 3 does the same with the linearised values, and clamps co to [0,1] before the sRGB encode so pow() never produces NaN. Neither choice affects the correct path.
- Mutation 19 ('coverage * w per child'): it is unspecified for nested groups and clip groups inside a pass-through group. I multiply w into every composite onto the running backdrop: LONE, isolated-group coverage, clip-group cg and clbl=false ci'. Nested pass-through groups multiply their own w in.
- BUILD-SPEC addendum D6 says to force xcb when DISPLAY is set, ignoring an inherited QT_QPA_PLATFORM. That conflicts with 'GUI tests run under QT_QPA_PLATFORM=offscreen, never a visible window'. I honour an inherited offscreen or minimal value, and `--smoke` forces offscreen itself.
- PNG reading for the io lane: bit-depth reduction is not specified anywhere. The reader uses png_set_scale_16 for 16-bit to 8-bit (rounding, not stripping) and does not canonicalise alpha-0 pixels; callers that store the pixels must apply C3.
- Doc 10 §13 lists hooks 16-18 and 21-22 as caught by goldens that the golden author writes. Locally they are proven only by unit tests; the smoke scripts do not trigger them.

## 2. Reference base (doc 10, conventions)

- C9 'Integers must be integral JSON numbers': it's unclear whether `2.0` counts as an integer. The reference accepts only JSON integer tokens (never bool), so `cell: 2.0` is a script error. The C++ side must do the same, or goldens should avoid it.
- C9 / doc 10 §11: duplicate JSON object keys and NaN/Infinity literals aren't mentioned. The reference makes both a script error.
- C10 'every document-changing op pushes exactly one record': it doesn't say whether an op that changes nothing (merge_visible with no visible node, reselect with nothing saved) pushes a record. The reference pushes one record for every op except undo.
- C10: the doc doesn't say whether undo itself creates a record, or whether redo exists. The reference: undo creates no record and there is no redo. History depth 1000 drops the oldest record.
- doc 10 §11 'Script shape (fixed)': it isn't said whether `out` (or `canvas`/`ops`) may be omitted. The reference requires all three keys and `out` must be "png8"; `canvas.bg` is optional as stated.
- doc 10 §11.2 add_mask: the 'fields that don't belong to the chosen fill are errors' rule is stated only for add_layer. The reference applies it to add_mask too (e.g. `value` with fill:"gradient" is an error).
- doc 10 §9.2 merge_visible: when nothing is visible it 'does nothing'; the doc doesn't say whether the `id` is still checked. The reference checks the id (non-empty, not a duplicate) only when a merge actually happens.
- My brief says 'selection mask + active flag', but doc 30 §2 says there is no separate active flag (all-zero = no selection), which matches C8a. I followed doc 30 §2: doc.sel bytes plus doc.sel_saved; no flag.
- doc 10 §9.1 merge_down 'the node directly above U does not have clip = true': I read this as that node's clip flag. A group above never blocks, since groups have no clip flag.
- doc 10 §11 rects 'may extend past the canvas': no bound is given on x/y/w/h. Huge values (past int64) would crash the reference as an internal error (exit 3) instead of a script error; either way the exit is non-zero.
- The CLI may be pointed at an OUT.png that already exists. C9 says 'writes no PNG' on error; the reference leaves any existing file alone rather than deleting it, so harnesses must check the exit code.

## 3. Reference: adjustments and filters (doc 20)

- doc 20 §B0.2 vs doc 30 §9: doc 20 says a filter with no `coverage` field uses M = 255 everywhere, while doc 30 §9 says every op that changes pixels honours the selection E. I followed doc 20 literally: a filter uses the selection only when given coverage {"src":"selection"}.
- doc 20 §B0.2 rect coverage: no defaults are given for x, y, w and h, so all four are required. x and y may be any integer, since no range is stated. w and h must be >= 0; value defaults to 255 and must be 0..255.
- doc 20 §B0.2 ramp coverage: `dir` has no stated default, so it is required ("h" or "v").
- doc 20 §A5 tint: only "#RRGGBB" or null is accepted; hex digits are case-insensitive, following the doc 10 §11 colour rule. "#RRGGBBAA" is an error, as err_bw_tint_with_alpha expects.
- doc 20 §A1: the rule in_black < in_white is checked after defaults fill in each setting, so {"in_black":254} alone is valid and {"in_black":200,"in_white":200} is an error.
- doc 20 §A2: a point that is not exactly a 2-element array of JSON integers is an error, so [255.0, 255] is rejected under the C9 integer rule. A key that is not an array, such as {"rgb": {}}, is also an error.
- doc 20 §A4: the valid ranges depend on `colorize`, so colorize is read first. With colorize, saturation defaults to 25 and hue must be 0..360. hue = 360 is accepted and wraps to 0 through the hc >= 6 rule.
- doc 20 §B0 lock: the lock step (F.A = O.A; F becomes (0,0,0,0) where O.A == 0) is applied before the coverage lerp, in the pipeline's order, and also when there is no coverage.
- doc 20 §B5 High Pass: in real arithmetic, (d/255 + 0.5) * 255 = d + 127.5 lands exactly on a rounding tie for every d != 0. Each byte is therefore decided by the last-bit rounding of d/255.0 + 0.5 and then * 255.0. Both implementations are IEEE and follow the stated order, so they should agree, but any reordering in C++ would flip bytes on every edge pixel. The doc may want to say so.
- doc 20 Part C: the doc's G01 figures (14 pixels changed by mutation 12, 2,881 by mutation 29) came from a prototype fixture. On the checked-in G01 fixture the reference measures 25 and 2,053; both mutations are still caught.
- doc 20 §B0: hidden layers are filtered, and the layer mask is neither consulted nor changed, as stated. A group or adjustment-layer target is a script error, raised by get_raster.

## 4. Reference: geometry and selection (doc 30)

- doc 30 §13 vs §2: §13 says that when both axes are unchanged 'the op is a no-op', but §2 lists image_size among the ops that clear the selection. My reading: pixels are untouched and the selection and its saved copy are still cleared, the same as §15's explicit 'a == 0.0: no-op (selection still cleared)'.
- doc 30 §15 + §11.4: in an arbitrary-angle rotate_canvas, the doc does not say what a layer-mask pixel becomes when its source position fails the §12.4 horizon or ±4 px range test. For raster layers that pixel is (0,0,0,0). For masks I store 255, because every tap would be outside, and outside mask taps are 1.0. No golden has a mask on this path, but the corners of a canvas rotated by about 45° hit it.
- doc 30 §12/§16 vs 00-conventions C8a: nothing says whether transform, or flip with a `layer` field, honours lock_alpha. C8a names only painting ops and filters, so both ignore the lock here.
- doc 30 §15: the normalised angle a = angle - 360*floor(angle/360) can round to exactly 360.0 for tiny negative angles (for example -1e-14), which breaks the stated 0 <= a < 360. I follow the formula literally: 360.0 matches no exact path, so it goes through the arbitrary bicubic path with rad = 2π, and the canvas size stays W x H because of the 1e-6 guard.
- doc 30 §19: no range is given for crop/select_wand/bucket_fill `x`, `y` (int), select_rect/select_ellipse `x`, `y`, the `points` coordinates, transform `translate`, `pivot`, `rect` x/y, the 9 `matrix` entries, or gradient `p0`/`p1`. I accept any finite number, or any JSON integer where the field is int. A huge integer that does not fit a double is a script error.
- doc 30 §19: the quad form requires `quad`. A script with only `rect` counts as the quad form and fails for the missing `quad`; it is not treated as the identity params form.
- doc 30 §7: sums over a padded row, as in a running-sum box filter, can exceed int64 on very large canvases at r = 250, even though every window sum fits. The reference relies on int64 wraparound being exact modulo 2^64. A C++ build that uses prefix sums needs the same care, since signed overflow is undefined behaviour in C++.

## 5. Reference: brush (doc 40)

- doc 40 §11 parity note 10 says lock recolours 'with the unlocked source-over colour', which contradicts §3.8's resolved 2026-09-26 rule (source-atop: Co = Cd*(1-a_s) + Cs*a_s, alpha byte kept), C8a and doc 10 §10. I followed §3.8/C8a; note 10 should be updated.
- doc 40 §4: after a non-aligned clone stroke writes clone_off, a later aligned stroke reuses that offset. This is the literal reading of the pseudo-code (non-aligned also assigns clone_off).
- doc 40 §4: clone_src/clone_off are 'not document state', read as living for one script run, not undone, and not shared between scripts.
- doc 40 §3.4 dab limit: the script error is raised when the 1,000,001st dab would be placed (exactly 1,000,000 is allowed). The eraser on a locked layer still runs the walk, so the limit applies to it even though the op changes no pixels (§3.8 / §7 say only that the pixels are a no-op).
- doc 40 §2.1 t_ms default 'previous sample's t_ms' is read as the previous sample's raw t_ms. Using te instead gives identical te values, so this is unobservable.
- doc 40 §2.2 target 'mask': the only error is 'no mask'. A disabled mask can still be painted, and the selection multiplies B for mask painting too (§3.8 writes a_s = B * s there).
- doc 40 §2.2 curves: points may be JSON integers ([[0,0],[1,1]]); any y outside [0,1] or any non-number entry is an error; 'first x exactly 0.0' is compared numerically (0 == 0.0).
- doc 40 §2.4 'source' coordinates: integers are accepted as doubles, and out-of-range or non-finite values are errors (the same rule as sample x/y).

## 6. Golden corpus: compositing + harness

- Doc 10 §12 says the goldens live in `tests/scripts/10-compositing/<name>.json`; the task assigns `tests/scripts/compositing/`. I followed the task, and the harness finds scripts in any subdirectory, so either works.
- C9 / doc 10 §11: any unknown top-level field is a script error, so a script carrying `"expect":"error"` would fail in both renderers for the wrong reason. The harness removes the `expect` key before rendering (other tokens, number text and duplicate keys are kept verbatim; the stripped copy goes to <out>/<name>/script.json).
- The task leaves `--expect-error-list` undefined. I implemented it as an optional FILE: with FILE, each non-comment line is a glob of golden names treated as expect-error, for scripts that cannot carry the key (e.g. invalid JSON). With no FILE, it prints the expect-error goldens and exits 0.
- The mutation-gate exit status with PENDING ids is ambiguous ('listed PENDING, not caught' vs 'exit non-zero if any id is uncaught'). My choice: uncaught or suspect ids exit 1 with 'SUITE IS VACUOUS FOR MUTATION n'; if only pending ids remain it exits 2, or 0 with --allow-pending. That way 40 pending ids can never look green by default.
- In mutation mode, a mutated CLI that errors on a script the reference renders counts as a FAIL (caught). If it errors on every script with no pixel mismatch at all, the verdict is SUSPECT (not caught), because that is what a CLI that doesn't understand `--mutate` looks like. Goldens that fail the unmutated baseline are excluded from catching.
- Doc 10 §12.1: 'ops (after which set_blend s <mode> with "seed":7)'. I put set_blend last in every config, after set_opacity and after add_mask, and gave every mode seed 7, not only diss. For bda, add_mask b comes before add_layer s, as the doc says.
- Doc 10 §12.3 / §12.4 / §12.6 leave child content, rects and colours open ('children use rects so they overlap partially', 'two children', 'three layers'). I fixed concrete values in gen_compositing.py: R1=[16,16,64,64] and R2=[48,40,64,64]; child 1 solid #E03020FF, child 2 a gradient ending at alpha 40 (grp_pass_opacity uses two opaque children instead); the mul child is gradient h #FF8040FF->#4080FFFF at [24,24,80,80].
- grp_nested ('pass ⊃ isolated mul ⊃ pass ⊃ over… children'): I read the '…' as allowing extra content. I added one Normal child at the G1 level and one at the G2 level, each below its nested group, plus two `over` children in G3, so the backdrop threading has something to thread.
- grp_iso_mask_diss: add_group has no seed field, so it is `add_group mode diss` followed by `set_blend g diss seed 9`.
- clip_invalid_base: §12.4 names no backdrop. I made the index-0 clipped layer a full-canvas gradient (the doc-12.2 backdrop colours), then a pass group with one child, then a clipped noise layer at [40,40,72,72].
- §12.6 gives no canvas size for the merge/flatten extras. I used 128×128, as in the rest of §12.2-12.5; the dkCl/lgCl tie cases use the stated 16×16.
- Doc 20 §A9 says add_adjustment has 'the same placement fields that doc 10 defines for add_layer'. The only one is `parent`, so that is what I use; `params` is omitted, since invert takes `{}`, the default.

## 7. Golden corpus: docs 20/30/40

- Paths: doc 20 Part C says goldens live in `tests/scripts/` and doc 10 §12 says `tests/scripts/10-compositing/`. I used the assigned folders adjust_filters/, geometry/ and brush/. The checker (gen/check_scripts_203040.py) is outside the assigned file list because the task asked for a checker without naming a path.
- Doc 20 C0: the fixtures are 'to be adjusted to doc 10's final field names'. I translated them to doc 10 §11.2 add_layer fill/from/to/dir and merge_down 'layer'.
- Doc 20 G19 is marked 'pending doc 10 op name'. I used doc 10 §11.2 `lock_transparency` with value true.
- Doc 20 FXR says 'over a white background layer', but its canvas row only sets bg #ffffffff. I used the canvas bg only and created no extra white layer (FXS likewise).
- Doc 20 C0 does not name the adjustment layer's id. I used 'adj' with default placement at the top of root. A22 omits params (A6 allows that); the other adjustment goldens pass params explicitly, {} where the doc writes {}.
- Doc 30 §20 'Unless stated, each selection golden ends with fill_selection L #1060e0ff': I applied this to SEL-* only. SEL-22 already ends with that fill. TR/RA/GR/BK get no trailing fill, because they are not selection goldens and a fill would overwrite their result.
- Doc 30 T fixture: 'gradient ... through select_polygon ..., then deselect' names the gradient first. I issued select_polygon (non-AA) before the gradient so that the gradient paints through it.
- Doc 30 SEL-18 'tol 0 contiguous aa false' I read as contiguous=true, antialias=false. For SEL-20/21/BK-03, where contiguous is not stated, it is omitted (default true).
- Doc 30 prose 'non-AA' is written as an explicit antialias:false even where that is the default (select_rect). 'aa' is written as antialias:true. Doc 30 'num' fields are emitted as JSON numbers with a fractional part (for example 8.0), which the doc allows.
- Doc 30 GR-04 gives its colours as '...'. I used #ff0000ff -> #0000ffff; any valid pair works because the zero-length gradient is a no-op.
- Doc 30 BK-04 says 'one opaque rect' with no position or colour. I used select_rect 22,24,20,16, fill #2040a0ff, then deselect.
- Doc 30 TR-14 says 'compared visually to flip h'. The golden stores only the transform result, as the doc says; no equality with flip is asserted.
- Doc 40 §9 leaves many parameters unstated. Where it does, colour defaults to #000000 by omission, except B16's second layer (#C03020), B17 (#FFCC00), B18 (#1E3A8A), B23 (#C03020 / #2040C0) and B24 (layer #C03020). My choices for sizes and positions: B03 at (32,32); B10 size 24; B11 size 36 on an S-curve; B12 size 40 on (16,32)->(240,32); B14 size 24 with 41 samples; B15 size 24 with pressure 0.2->1.0; B16 size 24; B17/B20 size 20 on the line (8,40)->(120,88); B18 size 22, hardness 0.7, opacity 0.6, flow 0.5; B19 size 24 on the B08 figure-eight; B21/B22 size 18, hardness 0.6; B27 size 16. Each choice is commented in gen_brush.py.
- Doc 40 B13 '2 dabs at constant pressure 128/255 and 127/255': I emitted two single-sample strokes (clicks) at (20,32) and (44,32), with pressures written as the doubles 128/255 and 127/255.
- Doc 40 B16 'wash and a second layer with buildup' on a 64x64 canvas with all 11 samples at (32,32): both layers are stroked at the same point, so the buildup layer on top partly hides the wash layer. That is the literal reading; its power to catch wash-only bugs is weaker than two separate goldens would give.
- Doc 40 B17/B20 'layer with an opaque disc on transparent': the disc is made with doc 30 ops (a non-AA select_ellipse over 32,32,64,64, then fill_selection #2060c0ff, then deselect), so every alpha byte is 0 or 255. Lock is applied with doc 10 lock_transparency.
- Doc 40 B21/B22 'layer with gradient + shape': an h gradient on L, a v alpha-ramp red layer merged down, an AA white ellipse and a half-alpha black rect, all through doc 30 fills. B21's first sample (64.5,60.25) makes rhu(-44.5) = -44 differ from round-half-away-from-zero (-45).
- Doc 40 B18: the doc does not say whether the layer is opaque. I used bg white with a transparent layer, select_ellipse (32,40,64,48) aa, then feather 8.
- err_undo_past_start assumes add_layer pushes a history record (00 C10: every document-changing op pushes exactly one). With add_layer plus one stroke there are 2 records, so steps 3 is past the start. If add_layer turns out not to push a record, the script still errors.
- The harness contract is my own decision: expect and equal_to are stripped by the harness before rendering, because doc 10 §11 fixes the script shape and C9 makes unknown fields errors. The harness author must follow tests/scripts/README.md.
- Doc 40 §2.5 marks undo as 'proposed here; owned by doc 10'. 00 C10 now defines it with the same grammar (steps int >= 1, default 1). B23 uses {"op":"undo"} exactly as doc 40 writes it.
